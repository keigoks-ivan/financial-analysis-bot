**1. 判斷物 5 個 FAIL，全是格式錯，流程停下等人。**

**2. 審核第一輪 🔴 1、🟡 4，修補後第二輪 🔴 0、🟡 2。**
第一輪紅燈：逐字稿摘要提到設備商把保固綁機台、OEM 在資料中心服務市場先卡位，判斷物沒接進 `moat.threats[]`，也沒寫 `evidence_dismissed[]`。修補後過。

**3. 審核員點名的資料級疑慮，其中一項正是這次改動要驗的。**

## 三、請 Codex 診斷的四件事

1. **審核段兩輪是否必要。** 第一輪紅燈是判斷者漏接一條反證，修補 agent 補上，第二輪過。新規則「修補後必重審」讓審核成本 $1.75 變 $5.17。請判斷：修補只改 `moat.threats[]` 一類新增條目時，能不能用機械檢查（新增條目的 `evidence_refs` 指到原本被點名的那條）取代第二輪 opus 審核。若不能，說明為什麼。
2. **修補 agent 為何修不到格式錯。** 17 筆 patch map 套用成功，但 5 個 schema FAIL 一個都沒碰。請看 `b1_patch` 提示與 patch map 的欄位範圍，判斷是修補 agent 看不到 FAIL 清單，還是 patch map 不允許改這些欄。Claude 的 normalize 補丁只是治標。
3. **`fact_refs` 缺席的處理口徑。** 判斷者從原始證據引數字時，規則要求寫欄位路徑、來源、期間。實跑中判斷者寫的是「逐字稿」而不是路徑。請判斷是否要在 `validate_judgment` 加一條：非 `fact_refs` 的承重數字必須帶 `evidence_path` 或逐字稿段落定位，否則 WARN。這是可追溯性問題，不是判斷問題。
4. **`decision_inputs` 三欄由誰回填。** 審核員無法判定 `moat.combined` 與 `score` 為 null 是腳本回填還是漏填。請確認這三欄的權威來源是 `dd_project.project` 還是判斷者，並讓審核契約寫清楚，避免每次都出黃燈。
