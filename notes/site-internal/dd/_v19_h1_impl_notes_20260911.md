# WP-H1 實作說明：v19 契約與渲染（2026-09-11）

範圍＝`_v19_plan_20260911.md` 第六節 WP-H1，且以第十節「Codex 複審後修訂」為準。**沒有跑模型、沒有跑 DD、沒有 push。** H3（軸觸發表）依複審不做。

規格檔：`scripts/dd_schema/judgment-v19.md`（欄位歸屬與投影規則全表）、`scripts/dd_schema/facts.md`（事實表）、`scripts/dd_schema/decision_inputs.md` §7（終端年契約）。本檔只記「怎麼做的、驗到什麼、沒做什麼」。

## 一、判斷者填什麼、程式投影什麼

判別只有一個：`meta.contract` ＝ `"v19"`。沒有這個標記的檔案，驗法與渲染**一個分支都不走**。

**judge-owned**（判斷者明示，缺就讓檢查報缺）：六問 `answers`（每題＝結論句＋短理由＋`fact_refs[]`＋結構化判斷值）、`scenario_inputs`（三支 EPS 路徑／終端倍數／機率／`max_dd.lo/hi/basis`）、`counter_evidence`（三視角反證、矛盾裁定、`triggers[]`、`kill_metrics[]`、`action_conditions`）、`decision_inputs` 九欄（`signal`／`ma`／`cycle_position`／`cycle_verdict`／`thesis_irreconcilable`／`valuation_dependent`／`market_wrong_reason_given`／`momentum_overheated`／`cycle_gates_pass`）、`thesis`、`appendix_a` 七欄、`eps_meta`。

**程式投影**（`scripts/dd_project.py`，25 條規則 P-01…P-25）：`archetype`／`industry`／`moat`／`growth`／`quality`／`governance`／`valuation`／`trap_analysis`／`premortem`／`contradictions`／`triggers`／`kill_metrics`／`evidence_dismissed`／`reasoning`／`plain.six`／`catalysts`（判斷者沒給時）／`decision_out` 的 rearm 與 exec_line／`decision_inputs` 十三個機械欄＋分母兩欄／`scenario.json`（`dd_scenario.py` 的輸入檔）。

逐欄歸屬與規則編號見 `judgment-v19.md` 第二、三節，這裡不重抄。

**界線（Codex 第 2 題的翻譯）**：程式只做「已給輸入下的算術與映射」——`path_risk` 依既有切點（🟢 ≥−30／🟡 −30～−50／🔴 <−50）從 `max_dd.lo` 轉燈；`capalloc_grade` 依既有計分卡（適用項 ≥2 過＝A、1＝B、0＝C）從判斷者明示的三項適用性與通過與否加總，三項皆不適用就留空；`moat.combined` 缺時取 execution／pricing 平均、`score` 缺時取 combined。**不做的**：`moat.grade` 不從分數推（17 份實檔查證：8.5 分同時對應 A（AVGO／CDNS）與 B（BWXT），映射根本不成立）、`val_light` 不從分位推、品質分與 `signal` 不推、Max DD 範圍不從情境樹反算。缺判斷值時投影留空，讓 schema `required` 與既有檢查報缺——測試 `test_v19_missing_judgment_value_is_not_backfilled` 就是釘這條。

## 二、四個接線界線怎麼落地（Codex 開工前提）

1. **一處程式轉接**：`dd_project.view_for()` 是唯一入口，接在五個消費端的**載檔點**——`validate_judgment.validate_file`、`gen_dd_tables.main`、`dd_brief.main`、`dd_bundle.cmd_gate`（只給 `gate_view` 用，③ 段的 judgment 全文仍附**原始 v19 檔**，閘看的是判斷者實際寫的那份）、`dd_delta` 的 `cmd_generate`／`cmd_check`。舊形狀時它回傳**同一個物件**（identity），所以既有行為不可能被改到——測試逐份斷言 `view_for(raw, path) is raw`。
2. **正規化不代填判斷**：見上。另加一條反向檢查——判斷者若手填了會被投影覆寫的 13 個 `decision_inputs` 機械欄（非 null），`validate_judgment` 直接 FAIL，不靜默取一邊。
3. **delta 是受測功能**：本包只做到「`dd_delta` 讀投影視圖」，DRIFT_WATCH 的欄位路徑語義因此不變。`section_map.json` 加了 v19 路徑對映，但**刻意沒把裸 `counter_evidence` 映到 `decision`**——`decision` 在 `always_rewrite_sids` 內，映了會讓 `dd_delta check` 把反證紀錄與矛盾裁定一併變成「永遠允許改動」，比舊形狀寬鬆（舊形狀 `contradictions`→s11、`premortem`→s12 都不是永遠允許）。只逐條映 `triggers`／`kill_metrics`／`action_conditions` 三個本來就住在 decision 段的子塊。真正的 delta 測試（含實質變動的第二次跑）屬 H2 之後。
4. **驗收不保證全綠**：改前先把 36 份舊格式判斷檔的 PASS／FAIL 基準存下來（`scratchpad/wph1/baseline.txt`），改後逐行比對**完全相同**——22 PASS／14 FAIL，FAIL 的那 14 份本來就 FAIL，沒有為了好看去修。

## 三、`facts.json` 怎麼做的

- **schema**：`scripts/dd_schema/facts.schema.json`。六問各一組事實，每條有穩定 id（`^f_[a-z0-9_]+$`）、`value`／`period`／`unit`／`basis`／`kind`／`source`（定位到 evidence finding id、`numbers` 路徑、逐字稿檔＋段落、digest item）；承重或衝突項附 `quote`。`kind` 四值：`realized`／`guidance`／`estimate`／`claim`——**「將成長」記為預期不記為事實**，抽取器對含「展望／指引／預估／目標／guidance／outlook」字樣的 KPI 自動落 `guidance`（FIX 的「管理層 FY2026 全年展望」即由此分類）。
- **`findings_digest[]` 不按方向裁掉**：`coverage`／`events` 逐條照抄，查無料的軸也留一條 `{axis}#none`。FIX fixture 48 條：正向 24、中性 7、負向 14、查無 3。id 算法與 `validate_judgment` 的 J1 完全一致（無 id 時 `{axis}#{index}`），兩邊才對得上。
- **抽取器**：`scripts/dd_facts.py extract`（零 LLM），從 `evidence.numbers` 抽 38 條機械事實（最新一季 KPI 逐項、同業利潤率、價格、26 週報酬、RSI、共識三年與修正、三把 trailing 倍數與分位、Forward P/E），其餘**留空並標 `needs_sonnet`＋一句說明**，不假裝完整。另補一條 `f_consensus_rev_3m_fy1_pct`（最新快照 ÷ 90 天前快照）——實測 13.58%，與 FIX v18 判斷檔手填的 `consensus_rev_3m_pct` **同值**，這欄從此不需要判斷者抄。
- **fixture**：`scripts/tests/fixtures/facts_FIX_20260911.json`（77KB）＝抽取器產物 ＋ 18 條手補（判斷實際引用到的分部占比、訂單年增、模組化產能、淨現金、股息加幅、Hunt 併購、歷史低檔倍數、訴訟與監管事實…），共 59 條；六題中五題仍標 `needs_sonnet`（缺的東西逐題寫明），另有 3 條 `gaps`。**這份 fixture 不是「完整的事實表」，是「機械層能做到哪、剩下什麼要 H2 的事實表 agent 補」的證物。**

## 四、v19 judgment fixture 怎麼做的

## 六、刻意沒做／拿不準的事

1. **`ddreport.py` 沒接線**。v19 run 要跑起來，`_judge_check()` 得改成「先 `dd_project.py view` 產投影檔 → 對投影檔跑 `dd_decision.py run` → 把 `decision_out` 併回 v19 原檔」，因為 `dd_decision.py`（依派工單不動）只讀 `decision_inputs`，而 v19 的原檔只有 judge-owned 九欄。本包提供 `dd_project.py view` 這個 CLI 與測試，**接線留給 H2**（那是「判斷段一回合」的工作包，prompt 與流程一起改比較不會改兩次）。
2. **快速版沒有為 v19 做新版式**（持有人 2026-09-11 範圍變更：拿掉快速版、v19 唯一產物是完整版）。`dd_brief.py` 只做最小相容——經投影視圖渲染，舊形狀逐 byte 不變。v19 檔渲染出來的快速版會出現六問、三視角、觸發器與數字（測試有釘），但版式沿用舊版，沒有做條列白話改版。
3. **完整版散文只有骨架**。`dd_project.py prose-stub` 把六問的結論句、短理由、引用事實、三視角、矛盾裁定排進 `<section id="sX">`，讓 `render_dd.py --assemble` 對 v19 run 組得出完整版（實測 48.8KB，13 段散文＋機械三段＋七表全注入）。**外資報告風格、條列白話是 H2 散文 prompt 的工作**，本包不寫文案——`section_map.json` 已保證每段拿得到該拿的東西。
4. **`facts.json` 的事實表 agent 沒做**（H2 的 `facts.md.tmpl`）。現在六題有五題標 `needs_sonnet`，缺什麼逐題寫在 `needs_sonnet_note`。
5. **`catalysts` 維持可選頂層欄**，不是純投影。`judgment-to-ddmeta.md` 明文 catalysts 與 triggers 是獨立居所（catalysts 常含觸發器沒有的事件），硬改成純投影會丟資訊；折衷是「判斷者給就用、沒給才從帶日期的 triggers 投影，`impact` 留空不捏造」。這條與計劃書第六節「catalysts 由程式投影」有出入，**是刻意的取捨，請複審裁定**。
6. **`required` 條目數沒有下降**（137→145）。如果持有人要的是這個數字變小，得再砍——但砍的會是 `scenario_inputs`（那是判斷，不能砍）或六問的四件式（結論句／理由／fact_refs／判斷值，砍哪個都會讓可追溯性掉）。我的判斷是這個指標本身不是目標，真正的目標是「判斷者少做幾件事、少跑幾回合」，那要等 H2 的實跑才量得到。
7. **`_projected_from` 標記**留在投影視圖裡（不進 dd-meta，白名單擋住）。好處是除錯時一眼看出這是投影視圖；代價是 J4 的「`plain` 數字 ⊆ 其他欄位數字」檢查會多收一個 token「19」，理論上可能遮掉一個 WARN。影響很小，但這是我知道的一個瑕疵。
8. **判斷 bundle 的 schema 速查還是舊形狀**。`dd_bundle._schema_cheatsheet()` 走的是 `judgment.schema.json` 的頂層 `properties`，看不到 `v19_contract`——所以現在對 v19 run 組出來的 `judge.md`，速查段仍是舊形狀。本包刻意不改（改了會動到所有既有 run 的 bundle 內容），**H2 換 `judge.md.tmpl` 時要一起把速查切到 `v19_contract`**，否則判斷 agent 會照舊形狀寫。
9. **不確定的一件事**：v19 把 `moat.spread_table`／`competitors`／`roic_durability.checkpoints` 這些表留在 judge-owned（因為舊形狀 schema 的 `minItems` 要求它們存在，投影視圖若缺就 FAIL）。它們有一半是事實（同業 P&L 對照），照 v19 的精神應該住 `facts.json`、由判斷者引用。本包沒動，因為動了就會改到既有檢查語義。若 H2 要搬，得同時決定舊形狀 schema 的 `minItems` 怎麼辦。
